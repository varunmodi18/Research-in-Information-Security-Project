# Behavioural monitoring (experimental): results 2026-10-23

Experimental. MAKA-E establishes who a device is; this monitor looks for authenticated devices that behave abnormally, which cryptography cannot rule out (docs/RESIDUAL_RISKS.md R-07, R-12). It runs at the base station on frames and security events the system already records, and only raises alerts: it never revokes, rekeys or blocks anything. The abnormal behaviour is injected faults in our own simulator, so these numbers do not transfer to real deployments.

Regenerate: `python -m maka.behaviour all` (docs/BEHAVIOUR.md).

## Isolation Forest explanations

Top-3 features by z-score, counted over correctly flagged windows (every flagged window is listed in the JSON file):

- excessive_rekey/default: frames_received (148), handshakes_completed (124), frames_sent (97), rekeys (60), handshakes_initiated (42)
- excessive_rekey/near_normal: frames_received (12), handshakes_completed (11), rekeys (7), frames_sent (5), handshakes_initiated (1)
- lossy_forwarding/default: rekeys (5), frames_received (4), handshakes_completed (4), frames_sent (1), seq_gaps_at_bs (1)

## Limitations

- Simulated data only: toy parameters, one frame per scheduler step, no radio loss or timing realism.
- Our own injected faults (excessive rekeying, lossy forwarding), chosen by us; other abnormal behaviour is untested.
- Alerts only: the monitor never revokes, rekeys or blocks a device, and an alert is not proof of misbehaviour.
- The near-normal rekey variant shows the limit: behaviour close to normal is mostly not detected.
- Thresholds are set for 1 % false alarms on benign validation windows; real traffic would need recalibration.
- Small samples (20 fault runs per variant, 16 benign test runs): a different random stream during development gave noticeably different numbers, so differences of a few points between the detectors are not meaningful.
